# Changelog

All notable changes to owui-mcp-spawner. The newest version is at the top.
Released versions are also tagged on GitHub; an in-progress section is kept up to
date as work lands, so it is never reconstructed from memory at release time.

## v0.2.2

**New**
- **A wrong parameter name now says which one was meant** — calling a tool with an argument it does not have produced `Tools.find_tools() got an unexpected keyword argument 'query'`: true, and the *right* name does not appear in it, although the runner has had the tool's schema in its hands the whole time. A small model that gets no usable answer invents a cause, which is the same rule the tool output already follows, one layer down. The message now names the parameter that is wrong, suggests the nearest real one where there is one (`'serch' — did you mean 'search'?`), names any required parameter that is missing, and lists what the tool actually takes with the required ones marked. It sits in the runner rather than in the tool router, so **every** tool reached through this framework gets it, not just the one where it was noticed. The sharp edge is telling a wrong *call* from a failure *inside* the tool: a `TypeError` raised deeper down must reach the caller unchanged, or the reader goes hunting for a parameter problem that is not there. That is decided by binding the arguments against the method's own signature — Python's own argument matching, so it knows that a tool taking `**kwargs` or dunder parameters legitimately accepts more than its schema lists, where a check against the schema would refuse calls that work. Nothing is refused in any case: the call has already been made by the time the question is asked, and without a schema the original exception text stands rather than being replaced by a message with no names in it
- **`manager_url` fills itself in** — a tool that talks back to the spawner (the router, the control tool) ships a default of `http://127.0.0.1:7860`, and on an installation whose manager runs anywhere else that default answered `find_tools` with "Could not read the catalog from the manager: All connection attempts failed". Clear, and avoidable: the manager knows its own address, and the runner already inherits it. The valve is now filled the same way the output-directory valves have been since Phase B — same rule, not a second one, and **a value set by hand always wins**. The bind address is turned into one you can connect to first: `0.0.0.0` is where the manager listens, not somewhere to dial, the same substitution the health check's probe URL makes
- **Backup and restore** — there was a per-instance export, but it hands OpenWebUI a connection entry: a URL and a token, no configuration and no code. And what is worth backing up is exactly what is *not* in git and not in the rsync — `configs/`, `tools/`, `runtime/`. If the disk of the machine this runs on died, the code was safe on GitHub and every instance definition was gone. **Settings → Maintenance → Backup & Restore** now writes the lot into one JSON file: the instance configurations, **their tool code**, the server settings, the access rules and the agent roster (hashed — `agent_identity` stores them that way precisely so this file can exist). The tool files were not in the plan's collect-list and are the bulk of the archive — 1.2 MB against 68 KB of configs on the live installation — and without them a restored config points at a file that is not there, which is worse than no instance because it looks installed. Deliberately not included, and named in the file itself: the venvs (rebuilt through the normal install path), the stored files under `content/` (that would be cloning a machine), the identity roster (rebuilds itself from the next call) and the usage numbers (history, not configuration). **Credentials are a checkbox.** With them the archive restores a working server and *is* a collection of credentials — the MCP, read and agent tokens, the user-JWT secret, the file key, and every API key in the instance valves; the filename says `-with-secrets` and the dialog says what that means, because a backup whose contents nobody can tell by looking is one that ends up in the wrong folder. Without them the file may be kept anywhere, and the price is stated too: no instance holding an API key will run until the keys are typed in again, and old download links stay broken because the file key is a different one. A redacted valve travels as a marker, and the restore **drops** it rather than installing `********` as somebody's API key — an instance with a missing key fails loudly, one holding asterisks fails in a way that reads like a broken tool. **One rule governs the whole restore: write only what is not there.** Not per category and not per switch — an instance whose id exists is skipped and named, a setting already set stays, an agent already known keeps its own hash, rules for a user who already has some are left alone, and `content.key` is written only where there is none, because replacing it silently invalidates every download link this server has ever handed out. On an empty machine — the case this exists for — nothing is there, so everything lands; on a running one a mistaken click costs nothing, which matters more here than anywhere else in this project. A port already taken on the target is reassigned through `find_free_port()` and **reported**, never quietly, so an OpenWebUI registration that still points at the old number is something you find out about here rather than in a chat window. **Check** runs the whole thing as a dry run and shows the same report without writing anything, and a real run that turned out to change nothing says so rather than reporting "Restored" over a list whose every line reads *kept* and *untouched* — replaying a backup onto the server it came from is the normal case, and it is the proof that a mistaken click costs nothing. Both routes are password-only and closed under `--no-token-edit`; the restore is the most destructive endpoint this project has, and it is in the `ADMIN_ONLY` list of the route sweep so that the test suite — which runs on the server — can never reach it
- **Test call from the dashboard** — from a chat window a failed tool leaves two candidates and no way to tell them apart: the tool is broken, or the small local model called a working tool wrongly. The info dialog now has a **Test** button per function that opens a form, calls the tool for real and shows the raw answer — verdict, duration and the **actual length in characters**, which is the recurring culprit with that model, since a default that returns too much gets truncated and a truncated result makes it invent a cause. The form is generated from the tool's own schema rather than being a JSON text box, because typing JSON by hand is how the wrong call gets made in the first place: string, number, boolean and enum get real fields with the required ones marked, and anything nested gets a JSON field **in the same form**, so no tool schema can leave the panel blocked however exotic it is. A field left blank is not sent, which keeps "call it without this parameter" expressible. Three outcomes are kept apart, because they send you to different places: the call never arrived (`Call failed`, with the cause unwrapped out of the SDK's `ExceptionGroup`), the tool answered with an error, or it worked. The client is the health check's one step further — `probe()` already had the Bearer token, the port-recycling guard and the shared-port URL, and only `call_tool` was missing — but with a budget of its own: 60 s instead of the check's 8, because a runner slower than that is unwell while a real call may legitimately generate a document, and the panel counts the seconds so a slow call looks slow rather than hung. **Callable as somebody.** The probe carries no identity, which is why an instance in `identity_mode: required` answers it with an empty catalog — a test call behaving the same way would be useless on exactly the instances one most wants to test. A *Call as* picker offers everyone the roster and the agent identities know, and the manager signs a short-lived user token with the shared secret for that one request; the same panel therefore answers "what does this user actually get to see?", which the rights dialog could otherwise only promise. An agent identity is signed the same way — its own token cannot be used, since those are stored hashed and cannot be reconstructed — and the runner resolves both paths to the same identity, so the rules that apply are the same ones. The claims are looked up **on the server**, never taken from the request, or the dialog could hand a tool a role its owner does not have and the rules would be tested against a fiction; a user nobody has seen may still be called as, because "what would a new user see?" is worth asking. Where the server has neither a user-JWT secret nor trusted headers the picker is replaced by the reason, once, instead of one silent *Access denied* per attempt. `POST /api/instances/{id}/call`, **password only** — it runs the instance's real code with the instance's real credentials, which no read-only or agent token may ask for — and refused on a locked instance, which is what the lock is there to prevent; the Test buttons are taken away there and for guests rather than being left to fail
- **Agent identities** — one token per calling agent, so Claude Code, Codex and a cron job stop being the same caller. Behind the shared MCP Bearer token they were indistinguishable: the access rules could not tell them apart, the usage figures counted them together, and the log said nothing about who it had been. The `machine_identity` added in v0.2.0 named them, but one name per *instance*, not one per caller. A named identity is issued under **Settings → Identity → Agent Identities**, appears in **Users & permissions** under its own id — before its first call, which is exactly when you want to give it its rules — and is revoked or re-issued one at a time. Called *agent identity*, not *agent token*: `MCP_MANAGER_AGENT_TOKEN` already exists and is something else entirely, the manager-API credential for agents that write. Assigned rather than proven — whoever holds the token *is* that agent — which is no weaker than the shared token it sits beside, and finally differentiable. The order is the part that had to be right: a signed user JWT beats an agent identity beats the machine identity, and a **broken** user token stays a refusal instead of falling through to the agent token beside it, or a forged JWT would be quietly demoted into a working identity. The runner's Bearer gate learned about them too, so an agent needs only its own token and not the shared one as well; a token belonging to nobody is still a `401`, and the shared token still opens the port exactly as before. Tokens are stored **hashed**, a deliberate break with the API tokens in `runtime/settings.json`: the point is that a backup of this file gives nothing away, and the price is that a token is displayed once, at creation, with a new one the only way back. A plain SHA-256 is enough where it would not be for a password — these are 256 bits of `secrets` output, so there is no dictionary to run. Two delivery paths, and a set environment variable wins, the same precedence `configure_api_tokens()` already uses: `MCP_AGENT_IDENTITIES` as a JSON list read once at start, for containers and units that want no extra state file, or `runtime/agent_identities.json`, written by the manager and only ever *read* by the runners — the `runtime/content.key` split, and for the same reason — where a revocation takes effect on the next call with no restart. Which path is in force is on the screen and in the API response, because "I changed the token and nothing happened" is otherwise the first question; and with the environment in charge the write routes answer `409` rather than `ok`, since the file they would write is not the file anyone reads
- **Health check** — the watchdog checked the pid, which answers "the process exists", not "the MCP server still replies". A runner whose event loop is blocked by a synchronous tool call, or one whose port was recycled by another instance, keeps its pid and stayed green in the dashboard while every call from a chat timed out. Once a minute the manager now makes the same request OpenWebUI makes — `initialize`, then `tools/list` — against each running instance, and the row gets a dot next to its status badge: green with the tool count, red with the reason. Nothing is inferred from a TCP connect, because an open port is exactly what a wedged process still has. An instance whose spawn lock is held is **skipped, not judged**: a start still in flight has no open port yet, and a verdict in that window would be a race rather than a diagnosis. Optional auto-restart, off by default and deliberately reluctant when on: a configurable number of consecutive failures first, then a growing wait (1, 5, 15 min), a hard cap of three restarts, and forgiveness only after half an hour of good behaviour — a tool broken for good must not restart itself every minute and bury the reason in its own log. Settings under **System → Health Check**. An instance in `required` identity mode answers the check with an empty catalog on purpose — the runner hides its tools from a caller it cannot identify rather than erroring — so its dot is green and the tooltip says why there are none, instead of leaving "0 tools" to read as "broken". The failure reason is unwrapped out of the SDK's `ExceptionGroup` before it is shown: "unhandled errors in a TaskGroup (1 sub-exception)" is true and useless, "All connection attempts failed" is what sends someone to the right place
- **System monitor** — the dashboard showed which instances run, never what they cost. A tile row above the table now carries CPU, memory, disk and network rate for the machine, and the table gained a RAM column: resident memory of the runner **plus its children**, because an instance that shells out to an agent CLI does its real work in a subprocess and charging the parent alone would show the busiest instance as the cheapest one. No GPU — every reading there is vendor-specific, and this framework has to run on whatever machine it is put on. Two rates need a previous sample to mean anything, and both report *nothing* rather than a fabricated zero until they have one: a `0 %` tile reads as "idle", not as "not measured yet". A counter that went backwards (an interface went down, the machine rebooted) is unknown, not a negative spike. `psutil` is a new dependency but an **optional import**: an installation that gets this code by rsync before anyone has run pip keeps serving, and `GET /api/system/stats` answers `available: false` with the command to fix it instead of a 500 that looks like a broken manager — the UI then shows that one line and stops asking, since nothing can change until the manager restarts. One clock, not two: the stats ride the dashboard's existing four-second poll, and they are fetched before the instance list so the RAM column and the tiles come out of the same round. Read-only, open to the read token, hidden from guests. Readers do not take each other's measurements: CPU and the network rate are both measured against the *previous* reading, so a second caller arriving within a fifth of a second takes no new sample and is handed the last one — before that, an MCP call landing beside a dashboard poll came back "unknown" while a perfectly good measurement existed, and a busy instance could report 0 % CPU. Found on the first live run. **Every mounted drive gets a tile**, not just the one the manager is installed on — a machine with a data disk and a backup disk was being described by its system disk alone, the least interesting of the three. Boot and EFI partitions are dropped by size rather than by path ("/boot" is a Linux name and this has to run wherever it is installed), and two mounts reporting the same size *and* the same free bytes count once — that is one APFS container seen through five volumes, or a bind mount, and separate drives never agree on free space for long. The install disk keeps its own marker, because it is the one that decides whether the next document can be written. Also reachable from a chat: the control tool (v0.0.11) gained `get_system_stats` — one prose line for the machine plus the heaviest instances, capped by a `top` argument, and an unmeasured value arrives as `?` rather than a zero a small model would report as idle. When the manager cannot measure, the tool hands over its reason verbatim instead of an empty result that invites an invented cause
- **Sort by RAM** — the memory column arrived unsortable, which made it a display and not an answer: finding the instance that eats the machine meant reading eight rows and comparing by eye. The header is now clickable like the others, descending puts the heaviest first. The value is not a field of the row — it comes from the system monitor and is joined in at render time — so both the sort key and the guard that protects a remembered sort had to learn about it: asking whether the *row* has an `rss` field would have refused the sort for everybody, not just for the guests the guard exists for. An unmeasured row (a stopped instance, or a manager without `psutil`) sorts as `-1` and so collects at the end opposite the heaviest, rather than being mixed in among the small ones — a dash is not a zero. Where nothing at all is measured the click is refused and the table keeps the server's order, instead of shuffling rows by a column full of dashes
- **Dashboard: status filter and pagination** — the table drew every instance on every poll, and the only way to find the one that failed was to read the whole list. A third dropdown filters by status; it is built from the statuses actually present, in lifecycle order rather than alphabetically (the order the Status column already sorts by), so it never offers a choice that comes back empty. Pagination sits below the table with 10/20/50/200 rows per page, and appears only once there are more instances than the smallest page size — a small installation never sees it. Two details it had to get right: the page survives the four-second poll (the re-render goes through the same path as every control, and only the table body is rewritten — the bar's own buttons are bound once), and a filter that shrinks the list under the current page pulls the user back instead of leaving them on an empty table. The page size is remembered in `localStorage`, the page number deliberately is not. Frontend only, no route touched
- **File storage** — tools that produce a file had nowhere to put it. An instance that opts in gets `content/<id>/`, and the path reaches the tool three ways (Valve autofill for `content_dir` / `output_dir` / `*_export_dir`, the `MCP_CONTENT_DIR` environment variable, and `MCP_CONTENT_URL` for the link), so a tool written for OpenWebUI usually runs unchanged. Results are rewritten on the way out: a link to OpenWebUI's `/cache/files/...`, which resolves against OpenWebUI in the browser and finds nothing of ours, becomes a download URL of the spawner's own. Each file carries a token derived from a server secret in `runtime/content.key` — deliberately not in `settings.json`, because the runners read it and a runner doing read-modify-write on that file would sooner or later overwrite a write of the manager's. The download route needs no login, the token *is* the credential, and a wrong token gives the same `404` as a missing file so the route cannot be used to probe for names. Quota with a warning line placed **before** the tool's own output (a small model reads the first lines), optional refusal once the folder is full, and retention by file age. Settings tab **Files**, per-instance switch in **Edit → Config**, and `list_content` / `read_content` / `delete_content` in the control tool (v0.0.8, deletion behind its own switch, off by default)
- **mcp 2.x** — the runner is on the 2.x `Server` API, the base packages are pinned to `mcp>=2`, and `require_mcp_2()` refuses to start on an older line rather than failing later with a missing attribute. This lifts the emergency ceiling from v0.2.1, where `mcp` had to be pinned *below* 2 because the 2.0 release rebuilt the API the runner used. The tool router had to follow to v0.0.9 — it is itself an SDK *client*, which the port had not accounted for
- **One endpoint per category** — registering tools in OpenWebUI was a choice between two extremes. One MCP connection per instance is precise and means maintenance per instance; the tool router is one connection but puts the model through `find_tools` → `describe_tools` → `call_tool` to reach anything. `http://<manager>:<port>/mcp/category/<name>` is the middle: every **running** instance of one category served as a single MCP server, with the tools under their own names and their own schemas. Tool names are `<instance-id>.<tool>` — always, not only on a collision, because clients read the tool list when they connect and a rename costs one reconnect, where a name that changes the day a second instance arrives costs a debugging session. The **dot** was not assumed: it is a real tool name here for the first time (in the router, dotted names are argument *values*), so it was measured on all three layers it has to pass — the MCP protocol lists and calls `demo.hello` and `demo.sub.deep` unchanged, OpenWebUI hands `spec['name']` on unfiltered, and the local model calls such a name and repeats it verbatim. A strict OpenAI-compatible function endpoint would reject it, and the README says so. **It runs on the manager port**, not on the shared port the sketch put it on: the shared port is off on the live installation, so an endpoint that only existed there would have been unreachable, and a category endpoint should not cost twelve OpenWebUI registrations being re-typed first. That needed an ASGI **dispatcher in front of** the FastAPI app rather than a mount — `_revalidate_static` is an `@app.middleware("http")`, and Starlette middleware wraps the response of everything that reaches the app, including a streamable-HTTP session meant to stay open. The dispatcher is the piece the instance endpoints will move onto the same port through; `lifespan` still goes to the app, so the manager's startup is untouched. **It checks no rights of its own**: the caller's headers travel to the instance unchanged and the instance applies its access rules exactly as for a direct connection, the same arrangement the router uses — with the accepted consequence that the listing shows tools whose call the caller may later be refused, because filtering it here would mean a second copy of the policy that can drift from the first. The MCP Bearer token *is* checked at the endpoint, before the category is even resolved: it reaches a whole category, so leaving it open while every instance behind it is closed would be a door around the wall, and answering "unknown category" to an unauthenticated caller would list every category this server has to anyone who asks. An agent identity's own token opens it too, exactly as at an instance. **No session is held upstream** — every listing and every call opens its own MCP session to the instance and closes it again, which deletes the session-handling problem this feature was expected to be rather than solving it, and costs nothing because the runner shares one `Tools` object across all sessions anyway. A **stopped** instance is simply absent from the listing, and calling one of its tools answers that the instance is not running *and that the arguments are not the problem* — without the second half a model reads "not available" as its own mistake and retries with new guesses. A **silent** instance drops out of the catalog with a line in the manager log instead of failing the whole listing, so one wedged instance cannot take a working category off the air. Categories are never configured: one exists as long as an instance carries it, so there is no second place that can disagree with the dashboard. The name in the URL is matched case-insensitively and a name with spaces is URL-encoded. Two views of it, in the two places the two questions get asked. The **settings** section, directly under the switch that turns the feature on and only while it is ticked, lists every category with its instance and tool counts and its own **Export** button — writing the same OpenWebUI entry the per-instance export writes, one level up — because "which categories can I register?" is a set-up question, asked once, next to the switch rather than on the dashboard. The row is its own copy button: hovering swaps the counts for the URL in the same slot, so the address is checkable without a column of its own and nothing shifts, and clicking the category name puts it on the clipboard — which needed a fix of its own, see below. The list follows the **checkbox**, not the save — ticking it is the moment somebody wants to see what they are about to switch on — which is why `GET /api/categories` now answers `{enabled, categories}` and lists the categories either way instead of returning an empty list while the feature is off: "no categories" and "switched off" are different states, and a dialog that has to fill itself before anything is persisted cannot tell them apart from one empty array. Nothing is given away by listing them — every category is already on its instance's row, and the route needs a login — but the exports stay **disabled** until the switch is saved, because until then the URL beside them does not answer. The **dashboard** keeps a bar under the filter row for whichever category the filter is set to, which is the contextual half: you are looking at those instances and want their one URL. The bar is rebuilt only when its content actually changed, because the dashboard poll comes through it every four seconds and an `innerHTML` rewrite under a finger that is pressing Export loses the click — the same guard the category dropdown already has. The tool count in it comes off the health check rather than from probing every instance on each four-second poll, and reads *not measured yet* rather than `0` until the first pass has run. **Off by default**, switched on under Settings → System: one endpoint reaches a whole category at once, and an upgrade must not quietly open a door nobody asked for — the same rule the shared port already follows. Switched off the path is not intercepted at all rather than answered with a `403`, so it returns exactly what any URL this manager does not serve returns; measured both ways on a running manager, `POST /mcp/category/Spike` and `POST /voellig/andere/url` come back identically, and `GET /api/categories` comes back empty so the dashboard bar disappears without needing a flag of its own. The switch takes effect on the next request without a restart, and turning it off takes the open session managers down with it instead of leaving them idle until the manager stops
- **Instance endpoints on the manager port** — `/mcp/<id>` is now served on the manager's own port as well, the same streaming-safe forwarding the shared port does, but without a second port and a second listener. **Off by default**, with its own switch under **Settings → System → Instance Endpoints**: an instance bound to localhost becomes reachable from outside the moment it is on, and a new way in is opened by a person, not by an upgrade. Switched off the path is not intercepted at all, so it answers like any other URL this manager does not serve. The shared port is untouched by it and keeps its own switch, so URLs already registered against it keep working. `category` is now a reserved instance ID — it belongs to the category endpoints.
- **A weekly test run on the server** — `deploy/run-suite.sh` plus a systemd timer, both in `deploy/`. A suite that is green on the machine it was written on says less than one that is green on the machine that serves; twice now a defect was invisible on the laptop and only showed up on the server. The script copies the code to a scratch directory and runs the suite there, leaving `runtime/` and `content/` behind, then checks that the live `runtime/` really was not written to.
- **Control tool v0.0.13** — `list_instances` answers with one line per instance (status, id, category, port, tool count, and whatever is worth knowing besides), with the full records behind `detail=True`: sixteen instances were several hundred lines, and a small model that runs out of room mid-answer starts inventing. Three things it could not reach at all are reachable now: `list_categories` (the category endpoints and their URLs), `list_agent_identities` (who may call with their own token — never a token, never a hash) and `check_backup` (what a backup would contain; the archive itself stays in the web UI). `get_settings` finally says what it actually returns, health check and endpoints included.
- **The `category` in the URL is a setting now** — `/mcp/<segment>/<name>`, changed under **Settings → System → Category Endpoints → URL segment**; every URL and every export follows immediately, no restart. It is validated rather than accepted: one path element of letters, digits, `-` or `_`, and never a word an instance already answers to — that instance would sit behind the category endpoints and be reachable nowhere. The reserved instance ID follows the setting instead of naming `category` once and for all, and moving the segment closes the open category sessions, because their address no longer routes.
- **A port of its own for the category endpoints, and one decision per way in** — `/mcp/category/<name>` and `/mcp/<id>` can each answer on the manager port, on a port of its own, on both, or on neither; two checkboxes and a port field per section, the same shape for both. Naming the same port in both sections is allowed and gives one listener that serves both paths. Listeners are kept by port rather than one per feature, and what a port serves is read per request — so moving a role between ports interrupts nothing that keeps its port. A port is refused when it is the manager's own or an instance's internal one (which is named in the refusal), and a port that cannot be bound puts the setting back instead of leaving a configured port the manager knows it cannot have. With a category port set, the list and the exports hand out that address. Listeners take their bind address from `MCP_MANAGER_HOST` (set by `app/manager.py` from `--host`) and fall back to `MCP_RUNNER_HOST` — same value on a normally started manager, but the public listener no longer hangs on a variable that is about where instances bind.
- **A way to remove a caller, not just to forget one** — **Settings → Identity → Known callers** lists everyone the runners have seen, every agent identity and everyone a rule names, each with *Remove*: the entry, the access rules and, for an agent, its token. Under deny-by-default that caller is refused from their next request on and comes back blank whenever they call again — the button exists for the moment somebody is misbehaving. It sits in Settings rather than on the permissions page because that page is for granting, and a destructive button on a daily screen is pressed by accident sooner or later. `DELETE /api/identities/<sub>/reset` needs the admin password, like `PUT /api/policy`: one line for everything that changes who may do what. The route is removal-only by construction — it deletes a key and never writes a policy a caller supplied.

**Fixed**

- **A fresh installation could not run five of the suite's sweeps** — with FastAPI 0.141 and newer, `include_router` no longer copies the included routes into `app.routes`; a single wrapper object sits there and the routes live one level down. The five contract and permission sweeps in `tests/test_api.py` read `route.path` off that collection and errored with `'_IncludedRouter' object has no attribute 'path'`, so anyone installing from `pyproject.toml` today got five errors on their first run. The tempting repair — skip whatever has no `.path` — would have turned the suite green while testing *nothing*: under the new FastAPI not one `/api` route is registered directly any more, so all five sweeps would have swept an empty list, and the read token and agent token would have been pinned by no route at all. The enumeration walks into the wrapper instead, and finds the same 58 routes under 0.136.1 and 0.141.1. Test code only; the framework's routing was never affected, only the test's view of it
- **Switching a venv or changing a dependency answered 409 with nobody else there** — the guard that asks whether anything moved under a running change compared the freshly read config against the state the request *wanted*, not the state it started from. A plain venv switch therefore conflicted with itself: `default` on disk against `alternate` in the request, condition met, `409`, nothing saved — after the packages had already been installed. The same for adding, changing or removing a dependency through that route. It compares against the state the request started from now, captured before a single field of the body touches it. What let this through matters more than the mistake: every concurrency test was green, because they all expected a `409` and got one for the wrong reason, and there was no test at all for the ordinary single request. There is now — switch the venv, add, change and remove a dependency, both at once, and a change that prepares nothing
- **One change at a time per instance** — the routes that save a config or a tool's code prepare an environment from one state and write into another, and checking the state again at the commit closed one interleaving at a time while the next one stayed open: three rounds of review, three more orderings. The last was the mirror of the one before it — a venv change starts, a code save finishes in the meantime, and the comparison of "prepared for" against "about to save" agreed because the request sets the venv itself. So an instance is now held for the whole route, and a second change to it answers `409` instead of queueing. Not queueing on purpose: a request that sits out a pip install is worse than one that says "not now", and waiting on a lock inside an async route would stall every other request in the process. Locking an instance stays possible at any moment — it is a safety action, not something to refuse for the length of an install — and a save that finds a lock at its commit writes nothing at all. The checks at the commit stay as well: they cost nothing and make a path that forgets the lock fail loudly instead of quietly
- **The conflict note adopted somebody else's problem** — what an install leaves behind is recorded per venv so a repeat cannot read its own damage as pre-existing, but the whole of `pip check`'s output was written down, including the foreign conflicts that had been exempted a moment earlier. A pre-existing problem in a shared venv would therefore have become permanently *ours*, blocking every later install there. Only what this install introduced is recorded now
- **A code save did not check that its environment was still the right one** — the config is read again before writing, but what the install and the validation were *for* was not. Move the instance from `default` to `alternate` while a save is validating, and the save writes the code's dependency onto the `alternate` config although only `default` was ever prepared: the target environment is missing exactly what the saved code needs. The venv a save was prepared in is compared at the commit now, and a save that finds a different one answers `409` and writes nothing. The config route got the same check for the case where it installed. And the merged dependency list — computed before the install, therefore older than anything saved since — was still written *over* the current one, dropping a dependency somebody had added and installed in between; it is merged onto the list as it stands at the commit instead
- **Repeating a failed install reported success** — an install that ends inconsistent leaves the packages where they are, so on the next attempt `pip check` says exactly what it said before and the "already there, not ours" exemption applies. The same call, run twice, therefore came back `(True, "")` over a venv that was still broken — confirmed against real pip. What an install leaves behind is now noted per venv, and while that note stands those lines get no exemption. When the conflict disappears the note goes with it, so a genuinely foreign problem is still never blamed on an install that did not cause it
- **Removing a caller could hand their access back** — *Settings → Identity → Remove* deleted the personal policy entry, and rights that come from the signed **role** survive that deletion, so the button that promises refusal returned a role-holder's access on their very next call. Worse the other way round: an entry that was itself a ban got deleted too, which meant Remove could *unblock* somebody. It writes a ban now rather than removing one — `{"deny": true}`, which stays until it is taken away in the permissions dialog. The lighter `DELETE /api/identities/<sub>` is still there for tidying a list. The confirmation, the success message, the hint on removing a single rule ("they will then reach nothing" was never true beside a role) and the README section were corrected with it
- **An explicit ban was ignored where the default was open** — `rules_for()` returns None for a personal `deny: true`, and `allowed_tools()` read that same None as "not listed", which an installation with `default.deny = false` waves through. So an explicitly banned person was granted *every* tool, on exactly the installations that had opened their default. "Named and refused" and "not named at all" are two different answers now, and the ban outranks the role, the default, and any e-mail or name a rule can be matched by
- **One pip call per requirement knows nothing about the others** — each dependency was installed on its own, so two of them could disagree about a shared package: the second call replaces the version the first one needed, both exit 0, and the function reported success over a venv that contradicts itself. It surfaces at import time, in a log far from the install that caused it. They go into one call now so pip resolves them against each other — checked against real pip with locally built wheels, where the impossible combination is refused as `ResolutionImpossible` *before* anything is written, which is better than reporting the damage afterwards. And exit code 0 is no longer taken as proof: `pip check` runs before and after, and anything newly complained about belongs to this install. Before as well as after, because a shared venv may already be inconsistent and no later install should fail for a problem it did not cause; a `pip check` that cannot run lets the install through, since a guard that cannot work must not block everything. Not done: preparing the change in a separate environment so a failed install is guaranteed to leave the working one intact
- **A long save could finish by writing an old config back** — saving code installs packages and validates in the venv, minutes of it, and then wrote back the config that was read at the beginning, overwriting whatever had been saved meanwhile. A valve value set in between was gone, and `locked: true` with it — a flag somebody set to protect the instance, cleared by a save that began before they set it. Both write routes read the config again before writing now, under one lock per instance, and set only the fields they own; the lock flag is checked again there rather than only at the door, because locking is exactly what somebody does *while* a long save is running. A save that finds a lock answers `409` and writes nothing at all, the tool file included, so a refused save leaves no half state. The mirror case was not in the report but has the same shape — the config route waits for an install too — and is fixed with it
- **A stop that was still killing deregistered the runner that replaced it** — the stop raised the generation counter but did not keep the number it took. Killing a process runs outside the lock and can take seconds, and a start arriving in that window is accepted (`stopping` is not one of the states it refuses) and registers its runner. The old stop then wrote `stopped`, cleared the pid and emptied `pids.json` without asking whether it still spoke for the instance: both operations reported success, the new runner was alive, and nothing managed it any more. A stop now holds its own number and checks it before every write. When a newer start has taken over it still did what it was asked — the process it was told to end is gone — but the books belong to the newer operation. That also settles what a start during a stop means: it is the later intent and may take over
- **A stop between "starting" and the claim was forgotten** — a regression from the generation change itself. The start published its state first and took its number a moment later, so a stop running to completion in between merely raised the counter, and the start then claimed a *higher* number and looked perfectly current. Before generations existed the status check caught exactly this ordering. Announcing the start and claiming its number are one step now, under the lock a stop also takes: a stop is either entirely before it, in which case the start is the later intent and may proceed, or after it, in which case it takes the number away
- **An ordinary keyword list was lost by a redacted backup** — the secret-name rule compared substrings, so "key" fired on "keywords", "auth" on "author" and "key" on "monkey". While that only hid single strings it was ugly but survivable, because the edit dialog reads a config and writes it back and the value returns to its place. Once the masking reached into lists it stopped being survivable: `{"keywords": ["birds", "nests"]}` came out of a backup taken *without* secrets as two masks, and the restore then dropped them and reported them as missing credentials — a setting nobody called a secret, gone for good. Names are compared word by word now, split on separators and on camelCase, so `API_KEY`, `apiKey` and `app_password_file` all come apart while `keywords` stays one word; the common run-together spellings are listed as words in their own right, and what remains uncatchable is an unlisted invention, for which the answer is a secret marked as one in the valve schema rather than guessed from its name. Checked against the 121 valve names on the live installation: not one loses its protection, and not one gains it
- **A start that was overtaken published its own dead pid** — the spawn lock made each step indivisible, but a start still recognised a stop only by the shared status, and a *later* start sets that status back to `starting` and then `running`. So: start A spawns and waits for its port, a stop kills A, start B spawns and registers itself, and A then wakes up, finds `running`, concludes it was never stopped, and writes its long-dead pid over B's — in the instance state and in `pids.json`. The manager and the watchdog then follow a pid that is gone while B holds the port: the orphan from the other direction. Each start now takes a number, and so does each stop; whoever held the previous one no longer speaks for the instance, permanently — a later start counts further up, it can never hand an earlier one its authority back. The number is checked under the same lock the publishing happens in: before the spawn, before the pid is written, before a failure is recorded, and before `pids.json` is touched, which moved inside that lock for the purpose. The failure path obeys it too, because reporting a crash after a newer start has taken over would bury a runner that is coming up fine
- **A masked value in a list was filled in by position** — `keep_masked_values()` matched list entries by index, which is right exactly as long as nobody touches the list. The edit dialog can now touch it: delete the first of two accounts and save, and the second account was handed the first one's token. Not a lost secret, a *swapped* one, which is worse — it fails as a wrong login rather than a missing one, against somebody else's account. An entry is now matched by everything about it that is not masked. While the list still has the same length its own position is tried first and used if it still fits, which carries the ordinary open-and-save, an edit in place and two identical entries alike; otherwise it has to fit exactly one previous entry, which carries deletion and reordering. Fitting none or several is refused with a `422` rather than guessed — a renamed entry cannot be told from a new one, and deleting from a list of bare secrets leaves nothing to match on at all. The refusal says to enter the value instead of leaving the mask
- **A list of plain secrets was not masked at all** — the recursion asked the key's own name at every depth but stopped at the edge of a list, so `{"api_keys": ["…"]}` went out through the config API and into a redacted backup in the clear, while `{"api_key": "…"}` beside it was masked. A list has no inner names to judge by; the name above it is all there is, so its strings are masked now. A *dictionary* under a secret name stays exempt — it brings its own keys, and those are the better evidence. The cost is that `{"keywords": [...]}` is masked as well, because `is_secret_field` matches substrings and "key" fires on "keywords" — but `{"keywords": "…"}` has been masked that way since the first version of the function, so the list now agrees with what already applied beside it, and the write-back puts the value straight back. A redacted restore drops such an entry instead of installing eight stars as a key
- **A policy this server could not read was treated as an empty one** — `load_policy()` returns `{}` for a *missing* file without raising, so an exception means the file exists and is unreadable. The restore caught it anyway and continued with `current = {}`, after which `save_policy()` replaced the file wholesale. The promise that what is there stays therefore failed in the one case where it weighs most: a broken policy denies everything, the one written over it grants, and the report said the roles had been restored. The file now stays where it is, `policy_failed` names the reason, and the rest of the restore carries on. Repairing a damaged policy is a deliberate act, not a side effect of replaying a backup
- **The new restart warning claimed the old runner was still serving** — `restart_instance()` stops before it starts, so a start that fails leaves the instance **down**, not running the previous version. The three warnings added a day earlier said the opposite, which sends the reader looking for tools that are no longer there. They now say only what is known — saved, restart failed, reason — and point at the instance's status, which the refreshed list is about to show anyway. The control tool (v0.0.15) carries the same correction as an explicit instruction not to claim which version is serving, but to look it up
- **A backup taken without secrets could carry one anyway** — `mask_secrets()` walked the top level of an instance's valve values and stopped there, and the backup export carried a second copy of the same flat rule. Valve values are `dict[str, Any]`, so `{"connection": {"password": "…"}}` is a legal shape: the config API handed that password to anyone with the read token, and it travelled verbatim into an archive that labelled itself `contains_secrets: false`. One recursive rule now does the masking for both, at any depth and inside lists — but a key's own name decides and the rule does **not** spread to what sits under it, because `is_secret_field` matches on substrings and "key" and "auth" also fire on "keywords" and "author". The half that matters more than the fix is the way back: the edit dialog reads a config and writes it back, so it sends `********` where the credential was, and a recursion without a counterpart would have stored eight stars as somebody's password the first time anyone opened the dialog and pressed save. `keep_masked_values()` puts the previous value back at every depth before the update; a mask with nothing behind it is dropped rather than stored, and a redacted backup now names the nested credentials it could not bring (`connection.password`) instead of leaving them to be discovered on the first call
- **A confirmed stop could leave a runner running** — starting an instance holds its own lock across `ensure_venv()`, which builds an environment and runs pip: minutes, sometimes. A stop that waited for that lock would be a stop that hangs, so stop deliberately did not take it — and that is exactly how it could return "stopped" while the start was still inside the venv preparation. The start then spawned a runner anyway, noticed the stop afterwards, and returned an error **without killing what it had just created**. Status `stopped`, pid set, port held, and the watchdog only looks at instances marked `running`: nothing on the dashboard said anything was there, and the next start failed on a port nobody could account for. The two sides now meet on a second, short lock, held only for moments — start takes it to make the last cancellation check, spawn, and publish the pid as one indivisible step; stop takes it to mark the instance stopping and read the pid it must kill, then releases it and does the killing outside. Whichever gets there first, the other sees it, and a start that gives up now takes its runner with it. Slow venv preparation stays interruptible, which is the reason the arrangement is two locks and not one
- **Two creates of the same id both answered `ok`** — an instance id was checked against the configs on disk and then let go, while dependency installation and validation ran; only afterwards was the config written. Ports were already held across that window, ids were not. So two creates of one id both passed the check, both installed, both reported success with their own port, and the second config simply overwrote the first: one caller was told about an instance that is not there, on a port nothing listens on. `reserve_id()` now checks and reserves under one lock and holds the id until the config is written or the attempt fails — in create, in both upload paths and in the restore, so they cannot race each other either. A second request for an id currently being installed is told so with a `409`; two *different* ids are still created side by side, because serialising every install would be a cure worse than the disease
- **A restore quietly dropped roles and the global rules** — the export carries the whole identity policy, and `_restore_policy()` wrote back `users` and nothing else: `roles`, `default` and `match_email` were read and discarded, and a policy that grants access by role and lists no individual users was skipped entirely for having no `users` key. The restore reported success, and the installation it produced denied the very people the backup listed — role-keyed rules match nobody once the roles are gone. All four sections now come back under the same rule the rest of the restore obeys: what the target already has stays, so a server that has already decided how to treat unknown callers does not get that decision changed by a file. The report names roles and globals separately, and a policy the validator refuses is reported as refused instead of being claimed as restored
- **A failed restart was reported as a completed one** — `restart_instance()` answers with a reason when it fails, and the two routes that save a config or a tool's code threw that answer away and set `restarted = True` unconditionally. So a restart that could not finish — a port taken in the meantime, a venv that no longer builds — reached the dashboard, the control tool and any agent as a change that was live. It was not: the old runner kept serving the old code, and nothing said so. Saving and activating are now reported separately. `ok` still means the file was written, `restarted` means the runner actually took it, and a new `restart_error` carries the reason; the editor, the config dialog and the update-from-example button say the instance is still running the previous version instead of showing a green success, and the control tool (v0.0.14) spells the same thing out for a model rather than leaving it as a field in the JSON
- **Saving code emptied the tool's manifest** — the tool JSON was rebuilt from scratch on every save, so `meta.manifest` came back as `{}`, `created_at` was reset to now, and any field an import had brought along was gone, after a save that changed one line of Python. A tool imported from OpenWebUI lost its author and version on the first edit; where the version lives only in the manifest, that is where the version display loses its source, and the next export no longer carries what the first import did. A save now updates the file in place: the code, the schemas generated from it, `updated_at`, and the three fields the config owns — everything else stays. Generating a fresh file remains what happens for a tool that has no previous JSON, which is the honest answer there
- **A structured valve value did not survive the edit dialog** — the form is flat: every value went into a text field through `String(v)` and came back from there. For a valve holding a structure — `values` is `dict[str, Any]`, and that is exactly where the nested password above was sitting — the field read `[object Object]`, and opening the config and pressing save was enough to overwrite the structure with that string. Structures are now shown as JSON and read back as JSON; a field edited into something that is no longer JSON stops the save instead of writing the typo over the structure. And a structure is shown even when its name reads like a credential, because the server has already masked the secret leaves inside it and blanking the whole field would hide settings that are not secrets — the mask is put back on save either way. The suite has no browser layer, so this one is checked by syntax and by reading
- **Every instance start leaked a file descriptor** — the runtime log was opened for the child to inherit and the manager's own copy was never closed. One descriptor per start, invisible until an instance that restarts on every config change had been running for weeks. Found by the new lifecycle tests, which complain about it out loud
- **The test suite had a race of its own** — `test_instance_endpoint` tore down the shared manager-port client with a fire-and-forget task, which could close it *during the next test's request*; that test then received `503 MCP proxy is shutting down` instead of the `401` it was asking about. Harmless in the small, and invisible until the suite grew enough to shift the timing. The teardown is awaited now, and the assertion prints the body it got — a bare `401 != 503` says nothing about which of the three 503s it was

- **Copying to the clipboard never worked over plain HTTP** — `navigator.clipboard` exists only in a secure context, and this manager is normally reached at a LAN address without TLS. Measured on the live installation: `http://192.168.1.100:7860` reports `isSecureContext: false` and `navigator.clipboard` as `undefined`, so every Copy button in the UI went straight to its failure branch. The agent-token dialog had known this since v0.2.2 and made the best of it by selecting the text for copying by hand; the category endpoint could not even do that, because its URL is only visible while the row is hovered. Both now go through one `copyText()` helper that uses the modern API where it exists and the legacy `execCommand` path where it does not — which works on a plain-HTTP origin. The legacy path needs a real, focusable element (`display: none` leaves the selection empty and makes the copy a silent no-op) and the user gesture that is still in flight, so nothing is awaited before it on the path that will use it. Where even that is refused the message now names the cause — not on HTTPS or localhost — and prints the URL, instead of pointing at text the reader may not be able to see. Verified against a manager bound to a LAN address, reproducing the exact condition rather than testing on `127.0.0.1`, where the bug does not exist
- **The identity probe called an agent token an unsigned OpenWebUI header** (v0.0.4) — it decided the wording from `identity.signed` alone, a two-way test on a question that has four answers, so everything that was not a signed JWT was reported as "taken from OpenWebUI's plain headers — UNSIGNED, not verified". That sends the reader off to check `ENABLE_FORWARD_USER_INFO_HEADERS` for a setup OpenWebUI is not part of — in a tool whose entire reason to exist is that identity mistakes are otherwise silent. The machine identity had been mislabelled the same way since v0.2.0; the agent identity is what made it visible, on the first live call. Each source is now named for what it is, and the two assigned ones say *assigned, not proven* instead of borrowing the header wording
- **A setting that could not take effect was reported as saved** — `PUT /api/instances/<id>` merged whatever it was given into `values`, the instance's Valve values. A name the tool does not declare is skipped by the loader (`tool_loader` checks `hasattr` on the Valves class), so it was persisted, did nothing, and came back `{"ok": true}`. Found by sending `{"lifecycle": {"auto_start": false}}` as a value: `lifecycle` belongs one level up, beside `values`, so a valve of that name was invented while auto-start never moved and the checkbox in the UI — correctly — stayed ticked. An unknown name is now a `422` that lists the valves this instance actually has and points at the `lifecycle` field. The valve names are read out of the tool's own code — `class Tools` → `class Valves`, **parsed with `ast`, never executed**, because a config write has no business being an execution primitive. The first attempt asked `cfg.values` instead, on the theory that the install seeds it from `Valves().model_dump()`; the live retest killed it in one call, because the invented key was already sitting in `values` and vouched for itself. Valves that cannot be determined (tool file gone, no `Valves` class, code that does not parse) mean "cannot tell", not "has none", and refuse nothing
- **The control tool could not reach auto-start at all** — which is why it was attempted through the valve values in the first place. New `update_instance_lifecycle` (v0.0.12, valve `allow_update_lifecycle`) switches `auto_start` and `restart_on_change`; each takes "true"/"false" or nothing at all to leave it alone, and `update_instance_values` now names it in its own description so the next model does not have to improvise
- **Every runner log line appeared twice** — the manager's logger has its own stdout handler, and inside the runner the root logger has one too, so each record was emitted by both. `propagate = False` on the manager logger ends it. Long-standing; it only became obvious next to a newly added line
- **The restore refused every real installation while the suite stayed green** — found before it shipped, and only by pointing the finished UI at a running manager. `tools/*.json` files are OpenWebUI exports, which are a **list holding one tool object**; `tool_loader` has always taken the first entry of a list and a bare object alike. The restore checked for a bare object, so it rejected the tool code of every genuine archive — and passed its own tests, whose fixture was a dict invented for the occasion. The fixture now has the shape the files on disk have, and both are accepted, with a test for each
- **The test suite wrote into the live settings file** — `auth.set_agent_token()` does not only set an environment variable, it *persists* through `save_settings`, and one lockout test calls it to check that a valid token at the wrong door is not counted as a guess. So every suite run rewrote the real `runtime/settings.json` — on the server, the file holding the password hash, the three API tokens and the user-JWT secret. The content survived, because the test puts the old value back in a `finally`; but for the length of that test the live file carried a token that is printed in the test source, and a process killed in between would have left it there for the next manager start to load. Not a thing to leave resting on a `finally`. The test now points the settings file at a temp copy, the third helper of this shape after `isolate_agent_store` and `isolate_usage_db`. Found the way both of those were — by diffing the runtime directory around a suite run — but this one only shows on the server: locally the file the test rewrites holds nothing worth protecting
- **The test suite counted its own calls into the live usage database** — two tests in `tests/test_runner_identity.py` start a *real* runner over real streamable HTTP, and a real runner records every call it serves. So each suite run added rows to `runtime/usage.db` — on the development machine and on the server, where those numbers are the ones somebody reads in the dashboard. The handler tests beside them sidestep it by patching `record_call`; these two must not, because the whole path is what they exist to prove, so they get an `isolate_usage_db()` helper instead — the same shape as `isolate_agent_store()`. Found by the sentinel check that is now run after every posten: snapshot `configs/`, `content/` and `runtime/`, run the suite, diff
- **The test suite deleted real files** — `tests/test_api.py::AgentTokenTests` walks *every* method of *every* `/api` route with a valid token and lets them run for real. `DELETE /api/content` was the first such route without a mandatory instance id, so nothing upstream turned it into a harmless `404`, and the first run wiped the storage folder. The same suite runs on the server. Patched like `_restart_after_delay` beside it, and verified with a sentinel file that survives a full run — **any new writing route without a mandatory id has to be patched there too**
- **A named agent lost its identity at the tool router.** The router replaced the caller's `Authorization` with its own, so an agent arrived at the target as the shared bearer — and an instance with `identity_mode: required` refused it for having no user, which is exactly the distinction agent identities exist to make. The router now forwards the caller's agent token, gated by a new per-instance `forward_agent_token` (off everywhere by default): only an instance allowed to see that token gets it, because unlike a short-lived user JWT it is long-lived and opens everything that agent may do.
- **`/mcp/<id>` on the manager port left the instance ports open.** Only a shared port used to bind the runners to localhost, so switching the manager-port way on added a door instead of replacing one — every instance stayed reachable on its own port from outside. Either way in now binds them to localhost, and instances that are already running are restarted when the switch is saved. The dashboard row and the OpenWebUI export name the port that actually serves: a port of its own, else the manager port, else the instance's own address.
- **Switching category endpoints off could answer 500 for a switch it had flipped correctly.** `stop_all()` caught `Exception`, and `CancelledError` has not been one since Python 3.8 — a serve task that was already cancelled sent the error straight out through the settings route. Found by the weekly run on the server, on Python 3.14, while the same suite was green on the development machine.


## v0.2.1

**New**
- **Settings in tabs** — eleven sections in one modal had outgrown the dialog. They are now grouped into **Security** (password, edit mode, MCP endpoint auth, read token, agent token), **Identity**, **System** (shared port, venvs, server) and **Maintenance** (usage tracking, update check). The panels stay in the DOM, so loading and **Save Settings** still reach every field no matter which tab is open — saving remains one action for the whole dialog. The chosen tab is remembered in `localStorage` (in a `try`/`catch`: in a private window the access itself throws)
- **Login lockout** — three rejected credentials from one address cost 60 seconds, the next three 120, then 240, doubling without a ceiling; the API answers `429` with `Retry-After` and the login dialog shows a countdown instead of "wrong password". There is no login route to protect — the browser sends the password as a Bearer token on every request — so the counter sits in `app/lockout.py` where that decision is made, keyed by the connection's address and never by `X-Forwarded-For`, which a caller could write to dodge their own counter or run someone else's address into a block. A request carrying **no** credential is not counted (the UI asks before anyone has logged in, and a reload must not cost a strike), and neither is a *configured* token that merely lacks the scope for a route — that is a client at the wrong door, not a guess. Counters live in memory only: a manager restart clears every block, which is also how you get back in if you lock yourself out
- **Permissions dialog at scale** — a search over all tools (with a "10 of 152" counter, blocks holding a hit open themselves), a search over the people list, and instance blocks collapsed from eight instances up, each header carrying its status (*no access* · *all tools* · *7 of 86*). Filtering and collapsing only show and hide the rendered blocks, so a checkbox already ticked cannot get lost on the way

**Fixed**
- **A new venv installed an `mcp` the runner cannot use** — the base packages were unpinned, so any venv created after the release of `mcp` 2.0 got the 2.x line, which rebuilt the low-level `Server` API; every instance in that venv died at startup with `'Server' object has no attribute 'list_tools'`. Existing venvs keep the 1.x they installed long ago and show nothing, which is why this stayed invisible on a running installation — but a **fresh install of v0.2.0 was broken out of the box**, as was any newly created venv. `mcp` is now pinned below 2 in `venv_manager.BASE_PACKAGES` and in `pyproject.toml`, with a test that fails if the ceiling is dropped without porting the runner first
- **The permissions dialog painted over its own buttons** — its grid items kept their automatic minimum height, so the columns grew with their content instead of scrolling, and the overflow was drawn across the Save/Close bar (which has no background of its own). Measured at 900×500 with 86 tools: 199 px of overlap, now a 20 px gap and a scrollbar where it belongs
- **A leftover directory took the venv list down** — an interpreter migration parks the old venv next to the new one under a name like `default.py312-migrated-20260816-001110`. The listing asked `venv_dir()` about every directory it found, and the dot in that name raised out of the listing and took `/api/venvs` with it. Unnoticed since 16 Aug because the UI has a fallback and quietly showed only `default`. ## v0.2.0

**New**
- **Identity Probe** (`examples/identity-probe.json`) — one read-only tool, `whoami`, that reports who arrived at an MCP server, whether the identity was signed, and what the rules grant them. Ships with the spawner because every mistake in the identity setup is otherwise silent: a wrong secret, an unrestarted instance and a mode left on `off` are indistinguishable from a chat window. Prints a fingerprint of the shared secret instead of the secret, so both sides can be compared without either being shown (see *Per-user identity*)
- **Users & permissions** — a 🔑 dialog that assigns rights per person: the runners record every verified caller in `runtime/identities.db`, the dialog offers that roster, and per governed instance you pick *no access*, *all tools* or single functions. Roles work as base equipment (OpenWebUI sends no groups, but the role is signed), a personal entry adds to them, an explicit deny wins. Saving is live — the rules file is read per call. A rule naming someone who never called is shown and marked, because that is what a mistyped user id looks like
- **Machine identity** — `machine_identity` in an instance config stands in for callers without an OpenWebUI login (agent CLIs, scripts), so `required` no longer locks them out and the rules apply to them too. Assigned, not verified; a valid token still wins over it and a broken one is still refused
- **Per-user identity** — the MCP Bearer token says a client may connect; it never said *who* is calling, so a tool holding credentials of its own acted with the same rights for every user of an OpenWebUI installation. The runner now verifies the HS256 user token OpenWebUI forwards (`ENABLE_FORWARD_USER_INFO_HEADERS` + `FORWARD_USER_INFO_HEADER_JWT_SECRET`) and publishes the verified user for the duration of one tool call, in a `ContextVar` — never on the Tools instance, which is shared by every concurrent caller. Per instance, `identity_mode` is `off` (unchanged behaviour, the default), `optional` (identity passed on, nothing enforced) or `required` (no verified user, no call). Only HS256 is accepted — a verifier that honours the token's own `alg` can be told `"none"` — with 60 s of leeway on `exp`/`iat` for clock drift between the two hosts. Access rules in `runtime/identity_policy.json` map the user id to instances and tools, deny by default, and are enforced on the call, not just on the listing: hiding a tool is presentation, refusing it is the boundary. `account` / `credentials_file` let a tool act under the user's own backend account instead of one shared login — opaque to the spawner, one secret per file, `chmod 600`. Without a shared secret, `MCP_USER_TRUST_HEADERS=1` accepts OpenWebUI's plain user headers instead: enough to keep the users of one installation apart, but a claim rather than a proof, so it is off by default, a signed token always wins over it, and a broken token is refused rather than falling back to it. The tool router (v0.0.8) passes the caller on either way (see *Per-user identity*)
- **MCP tool router** (`examples/mcp-tool-router.json`) — one OpenWebUI connection with three meta-tools (`find_tools`, `describe_tools`, `call_tool`) instead of one connection per instance. Measured on a ten-instance installation: ~690 instead of ~11.600 tokens of schemas per request. Read-only, works with and without the shared port, refuses to route into itself or into the control tool (see *One connection for all tools*)
- **Declared categories** — a tool can name its default category in its docstring (`category: …`), used at install time when none is given. The shipped control tool and tool router declare `System`, which is also how the usage report keeps them out of the ranking
- **Usage statistics** — a report over all instances and their functions behind the 📊 button, plus `GET /api/usage`; the control tool gained `get_usage_stats` and `get_instance_specs` (v0.0.7), so an agent can evaluate the same data
- **Usage tracking** — every tool call is recorded with time, instance and function in `runtime/usage.db` (SQLite, stdlib). The info view shows how often an instance has been used, when last and which function; `never used` otherwise. Counted in the runner, so it works without the shared port, and only for `tools/call`. The event log is pruned to a retention window (default 30 days), the totals are kept, so *ever used* survives pruning. No arguments, no results, no caller addresses
- **Update hint for tools from `examples/`** — the dashboard compares an installed tool against the copy the spawner ships under the same id: a compact `↑ x.y.z` marker in the instance table, the full badge plus the source file in the info view. Both are buttons: they ask, then apply the shipped copy through the normal save path, keeping the Valve values and snapshotting the previous code to `runtime/history`. Forward only (`409` on a downgrade), refused on locked instances, hidden in read-only mode. The control tool aged unnoticed exactly this way, and the router was one day old before it was a version behind. Compared with `packaging.version`, never as strings The control tool aged unnoticed exactly this way, and the router was one day old before it was a version behind. Compared with `packaging.version`, never as strings. Reports only: an "update now" button would overwrite code you may have adapted, and is refused on a locked instance anyway
- **Info view in the dashboard** — an **Info** button per row opens a dialog with description, category, version, venv, status and the tool's function list (name, description, parameters with type and required flag). Read from the `specs` block of the tool JSON, so no instance has to run and no uploaded code is executed; available in every edit mode, hidden for guests (see *Info view*)
- **`GET /api/instances/{id}/specs`** — function catalog of one instance. Deliberately behind `require_auth` only, not `--no-code-edit`: these are metadata, not source
- **`GET /api/instances?include=specs`** — the whole catalog in one call, opt-in. Without the parameter the list payload is byte-for-byte what it was; guests never get specs
- **API tokens** — two optional credentials so a tool never has to carry the admin password, which lands in clear text in an instance config and can only be revoked by changing the password itself. The **read token** is valid on `GET` requests only (the tool router); the **agent token** on every method (the control tool with its write actions). The rule is the HTTP method, decided in one place, so a mutating route cannot forget to opt out of the read token. Both are refused with `403` on the routes that handle credentials: the three that return a token verbatim, the instance export (its payload embeds the MCP token), and `PUT /api/settings` — a token able to write a new password would be the password. Optional and independent, cannot equal the password or each other, managed in the Settings page or via `MCP_MANAGER_READ_TOKEN` / `MCP_MANAGER_AGENT_TOKEN` (see *API tokens*)
- **Update check** — optional, **off by default**: the server asks the GitHub releases API once a day whether a newer version exists and shows a badge in the header after login. Comparison via `packaging.version`, result cached server-side, browser never contacts GitHub, failures stay silent. A **Check now** button runs one check on demand — cache and switch ignored, with the result (and the reason on failure) shown right in the form; with the switch off nothing is persisted. Reports only — nothing is downloaded or installed (see *Update check*)

**Fixed**
- **Uploaded tools kept OpenWebUI's truncated `specs`** — an OWUI export often carries only the first line of each docstring, cut off mid-sentence, and sometimes misses parameters entirely. The upload path validated the code anyway and had the correct schemas in hand, but discarded them. It now replaces `specs` with the generated ones while keeping everything else the upload brought (`meta`, `manifest`, ids). Already installed tools are repaired **once, automatically**, by a background task on the next start (marker `runtime/.specs_migrated`); a file is only rewritten when the specs actually differ. The repair deliberately ignores the instance lock — `content` stays untouched, only a derived field is recomputed, and a locked instance is exactly the one that could not be fixed by hand. Matters now that the info view, the specs API and the tool router show these descriptions to humans and models

**Internal**
- **One version source** — `app/__init__.py:__version__` is the single place; `pyproject.toml` derives its version from it via `[tool.setuptools.dynamic]`. With the update check comparing against it, two places to bump would have meant false "up to date" reports

## v0.1.2

**New**
- **Shared MCP port** — all instances can be served through a single port as `/mcp/<id>` via a streaming reverse proxy; instances then bind to `127.0.0.1` only, so exactly two ports stay open (see *Shared MCP port*)
- **Categories** — instances carry a free-text category set on upload, in the editor or in Edit; the dashboard shows it as a column and offers a category filter plus a search box over ID, name, description and category. The label lives in the MCP config only, so setting it never rewrites the tool JSON/code or restarts the instance
- **Guest mode** — with auth enabled, the login screen can be dismissed with *Continue as guest*; `GET /api/instances` and `GET /api/instances/{id}` then return only `id`, `name`, `description`, `category`, `status` and `version`, and the UI hides ports, URLs, venv and all actions (see *Guest mode*)
- **Control tool v0.0.6** — `upload_tool` and `create_tool` accept manager categories; `update_instance_category` can change or clear them without modifying tool JSON/code or restarting the instance. The write actions also document the lock: code edit, config/values/dependencies/venv changes, restart, reinstall and delete state that a locked instance answers `403`, and `export_tool` states that it needs code-read permission. The shipped `specs` are regenerated from the code, so the descriptions an agent sees can no longer drift from the docstrings
- **Version badge** — the spawner's own version is shown next to the title in the header

**Security**
- **Only advertised tools are callable** — the MCP runner checks the requested name against the tool list built from the `Tools` class instead of resolving it with `getattr` alone, which also exposed private helpers and inherited methods
- **Subresource integrity for CDN assets** — the CodeMirror `<script>`/`<link>` tags carry SRI hashes, so a compromised CDN cannot inject code into the admin UI
- **CLI edit mode is locked** — a mode set via `--no-edit` / `--no-code-edit` can no longer be lifted at runtime through `PUT /api/settings`; the Settings dropdown is greyed out. Modes set via the Settings page remain changeable as before
- **Lock/unlock respects edit mode** — both routes now require upload or full edit mode and return `403` under `--no-edit`

**Fixed**
- **Dependencies starting with `http` were rejected** — the package-spec validator matched the prefix `http`, so `httpx`, `httpcore` and friends failed validation; it now only rejects `http://` and `https://` URLs
- **Bearer scheme is matched case-insensitively** — per RFC 7235 a client sending `authorization: bearer <token>` is no longer turned away by the MCP endpoint
- **Stop never lies about the outcome** — a runner that survives SIGTERM *and* SIGKILL is reported as still running instead of being marked `stopped` while the orphan keeps its port; killed children are reaped, so a zombie no longer counts as alive; `restart` aborts when the stop failed instead of starting a second process on the same port
- **Stop works during startup** — the runner PID is registered as soon as the process spawns, so stopping an instance in its startup window actually kills the process instead of leaving it running with status `stopped`
- **Port race on concurrent installs fixed** — auto-assigned ports are now held for the duration of the install, so two parallel uploads can no longer receive the same port; the shared proxy's port is reserved during allocation as well
- **ID `example` is reserved** — creating a tool with this ID used to overwrite the shipped `configs/example.json` and produce an instance that never showed up in the list
- **Atomic file writes** — configs, `pids.json` and `settings.json` are written via temp file + rename; a crash mid-write can no longer corrupt them
- **Robust request validation** — malformed JSON bodies (wrong types for `server`, `values`, `install`, `id`, `content`, `code`) return `400`/`422` instead of `500`
- **Settings save is change-aware** — an unchanged edit mode is no longer persisted to `settings.json` (which used to freeze a CLI-flag default) or reported as "Saved: edit_mode"
- **Readable error messages** — upload and config-edit dialogs now render structured `422` errors (e.g. a failed pip install) as text instead of `[object Object]`
- **Reinstall visible in readonly mode** — the dashboard now shows the Reinstall button in readonly mode, matching the documented API behaviour (it only re-runs pip for the already-pinned dependency list)
- **Log panel handles auth errors** — an expired session shows the login dialog instead of dumping a JSON error into the log view; `GET /api/instances/{id}` now includes the `version` field like the list endpoint
- **MCP token hint** — changing the MCP Bearer token in Settings now notes that running instances keep the previous token until restarted

**Internal**
- **API split into route modules** — `admin_server.py` shrank from ~1200 to ~140 lines; the endpoints now live in `app/routes/` with shared guards and serialization in `app/api_helpers.py`
- **Frontend split into ES modules** — `web/app.js` is a bootstrap; instances, config, upload, editor, logs and settings each own a module, with shared state and helpers in `common.js`
- **Faster instance list** — one directory scan feeds states and enrichment, tool versions are cached by mtime, and the disk walk runs off the event loop (the UI polls this endpoint per open tab)
- **Server-classified secrets** — `GET /api/instances/{id}/config` ships a `secret_fields` list so the edit dialog no longer has to guess which values are credentials
- **Test suite** — `tests/` covers the API contract, auth and guest exposure, locking, schema/package validation, port allocation and a full e2e lifecycle over HTTP and MCP
